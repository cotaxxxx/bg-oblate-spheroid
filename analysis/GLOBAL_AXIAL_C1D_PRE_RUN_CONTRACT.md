# C1d AXIAL UPPER EXCLUSION — MACHINE GATE PRE-RUN CONTRACT

**Status**: `PREDECLARED / MACHINE_NOT_RUN / NOT_BINDING`

## §1 Claim

```
partial_t^3 g_axis_ob(t,lambda) < 0     on  D := [0, 31/32] x [5/8, 33/50].
```

This gate certifies only the sign of the third `t`-derivative on `D`. It does not certify the right-endpoint anchor, the analytic bridge, or the absence of nonzero roots; those enter only in a separate assembly document.

## §2 Partition

**lambda.** Eight exact boxes

```
Lambda_k = [(1000+7k)/1600, (1007+7k)/1600],    k = 0,...,7,
```

whose union is exactly `[5/8, 33/50]`. These coincide exactly with the eight lambda boxes generated by the pinned lower-edge producer/checker of machine receipt `3e2dfb04`; this equality was verified before this pre-run contract was frozen (§8).

**t roots.** Sixty-two exact cells

```
T_j = [j/64, (j+1)/64],    j = 0,...,61,
```

whose union is exactly `[0, 31/32]`.

Root nodes are the 496 products `T_j x Lambda_k`.

## §3 Node procedure

For a node `(T, Lambda)` at depth `d`, with `T` a dyadic interval of width `2^{-6-d}`:

```
1. Evaluate with N_s = 2048.  If accepted, stop: record stage (d, 2048).
2. Evaluate with N_s = 8192.  If accepted, stop: record stage (d, 8192).
3. If d < 7: split T at its exact midpoint into two children of depth d+1,
   each paired with the same Lambda, and apply this procedure to each.
4. If d = 7: evaluate with N_s = 16384.  If accepted, record stage (7, 16384);
   otherwise the node is UNRESOLVED.
```

The evaluation order is fixed: children in increasing `t`, nodes processed depth-first. The maximum depth `7` gives minimum width `1/8192`.

**Acceptance.** A node evaluation is accepted if and only if the enclosure of `partial_t^3 g_axis_ob` over the node is finite and its upper bound is strictly negative.

## §4 Exception semantics

During a node evaluation, an exception of class `ValueError` or `ZeroDivisionError` is a failed evaluation of that node, and the procedure continues to the next step of §3. These are the box-local classes; the list is exhaustive. Any other exception is fatal and terminates the run as `ABORT`.

A nonfinite enclosure returned without an exception is not an exception case; it fails the acceptance criterion of §3 and is handled there. The driver tests finiteness of the returned enclosure before any conversion or serialization of its endpoints.

Both lineages catch exactly the classes listed above. Verified before freeze: producer `fbffaccc6dfcfd1b7b9be5b362d8cb80d867aa62` and checker `3ecbda1b3e9acd8134fdd94505721b1780e14edc` each wrap node integration in `except (ValueError, ZeroDivisionError)`.

## §5 Kernel and lineages

The evaluators are the C1c producer `fbffaccc6dfcfd1b7b9be5b362d8cb80d867aa62` and checker `3ecbda1b3e9acd8134fdd94505721b1780e14edc`, reused **byte-identically**. A new driver supplies only the node box and `N_s`. Producer at 160 bits, checker at 192 bits.

## §6 Checker

The checker does not rebuild the tree. It receives the producer's accepted leaf set — exact `(T, Lambda)` endpoints and the accepting `N_s` — and:

1. verifies that the leaves tile `D` exactly: no gaps, no overlaps, all endpoints exact dyadic in `t` and exact in `lambda`, union equal to `D`;
2. re-evaluates every leaf with its own lineage at the recorded `N_s`, requiring acceptance in the sense of §3.

Exact leaf data (endpoints, depth, `N_s`) must agree between lineages. Enclosure values are lineage-dependent and recorded only.

## §7 Budget and termination

```
MAX_ATTEMPTED_NODES     32768
MAX_TOTAL_PANEL_EVALS   2^28
```

A run terminates as `PASS` when every root is resolved into accepted leaves; as `UNRESOLVED` if any depth-7 node fails step 4; as `ABORT` on cap exhaustion or a fatal exception. `UNRESOLVED` and `ABORT` are fail-closed and record the offending node's exact endpoints and final enclosure when a finite enclosure exists; otherwise they record the applicable exception class or nonfinite outcome without converting nonfinite endpoints.

## §10 Implementation binding and execution provenance

**Implementation.** The driver is implemented in a single commit whose immediate parent is the commit freezing this contract; no rebase, amend, or intervening commit. That commit may add the driver and its tests; it must not modify the evaluator blobs of §5 or the artifacts of §9. Before the production run, the implementation commit receives a chat raw audit of the full text of every added or changed file, bound by blob SHA-1, and the §8.2 controls are run through it.

**Execution.** The production run uses a new run directory and records, before the first node and after the last: the exact HEAD (the implementation commit or a pins-only direct child of it), an empty `git status --porcelain`, the blob SHA-1 of the driver and of both evaluators, the interpreter path and version, the python-flint version, and the CPU description. Any mismatch between the two records, or between them and the pins, makes the run `NOT_EVIDENCE` regardless of its numerical outcome.

**Ledger.** The producer ledger is append-only JSON lines with a SHA-256 hash chain. Resumption is permitted only with identical pins and an intact chain; otherwise a new run directory is required. On completion the ledger is sealed as a mode-444 copy with its SHA-256 recorded, and the checker takes the sealed ledger as its only input.

**Order.** Roots are processed in increasing `j`, and within each `j` in increasing `k`.
